# ADR 0010 — WireGuard tunnels to sites whose databases are not exposed

Status: Accepted
Owner: TBD
Last updated: 2026-11-06

## Context

Some Copy & Sync sources and targets sit behind firewalls that will not expose database ports.
The orchestrator host (goldmine) is reached through a Cloudflare Tunnel, which cannot carry
WireGuard's UDP. Decided with the user: **each site opens one UDP port** for a WireGuard server
next to its database; our side dials out. All six tools must be able to use it.

## Decision

1. **A `cdc-wireguard` gateway written on wireguard-go with its gVisor netstack** — userspace, no
   TUN device, no `NET_ADMIN`, read-only root, all capabilities dropped. One wireguard-go device
   per tunnel, each on its own netstack.
2. **Tools use TCP forwards, not routes.** For a connection with `tunnel_id`, the orchestrator asks
   the gateway for a forward (`cdc-wireguard:21000-21999` → host:port inside the tunnel) and
   rewrites the sidecar payload's host/port just before a run or connection test. Sidecars stay
   on plain Docker networking and need no change. Forwards are added while tunnels run; they
   never restart a tunnel, so live CDC syncs are not cut.
3. **wireproxy was rejected** although it is built on wireguard-go: it reads forwards once at
   start, so a new profile would mean restarting the process and cutting running syncs.
4. **Secrets**: tunnel private and preshared keys are stored in rqlite (redacted `********` in the
   API, kept on update like database passwords). The gateway holds them in memory only; the
   orchestrator re-pushes tunnels when the gateway's reported `version` differs (30 s loop and on
   demand before a forward). Keys are generated by the gateway (Curve25519, `wg genkey` clamping).
   When asked to, the orchestrator also generates the site's key pair and returns the site's
   private key once in the site configuration; it is never stored.
5. **Site configuration is generated** (`wg-quick` file + checklist): site address/port, the
   gateway as the only peer (`AllowedIPs = <gateway>/32`, no endpoint), and forwarding + NAT rules
   when the database is on another host. IP forwarding is a persistent sysctl, not a `PostUp`
   command (a failing `sysctl` in `PostUp` aborts `wg-quick`). `docs/wireguard-sites.md` is the
   site-side guide.
6. **Limits**: Redis Cluster and MongoDB replica-set discovery redirect clients to node addresses
   a single forward cannot follow (Redis Cluster via a tunnel is refused with that reason). File
   sync through a tunnel always uses the relay transport (direct mode would have the source host
   dial the target itself). Postgres dump SFTP destinations are not tunnelled.

## Consequences

- One more sidecar (`cdc-wireguard`, ~18 MB) and env (`ORCH_WIREGUARD_URL`, `ORCH_WIREGUARD_TOKEN`).
- A gateway restart drops open tunnelled connections (running syncs fail and can be restarted);
  tunnels come back within one reconcile cycle without any change at the sites.
- Each site needs a UDP port forward and its database must allow the tunnel address (or the
  WireGuard host's LAN address when it masquerades).

## Verified

- Gateway tests: RFC 7748 key vector; a real round trip through two userspace WireGuard devices
  over loopback; a connection survives a peer reconfiguration; probe hints; token auth.
- End to end in Docker: site Redis on an internal network with no exposed ports; site running
  the generated `wg-quick` config verbatim (interface name and once-shown preshared key filled in);
  orchestrator → gateway → site; Redis sync connection test and one-time sync of all keys through
  the tunnel; gateway restart reconciled in ~20 s and the next sync succeeded.

## Rejected

- **Kernel WireGuard in the sidecars / host routes** — needs `NET_ADMIN` in every sidecar and host
  routing changes.
- **Sites dial in to our server** — needs a public UDP port on goldmine (Cloudflare cannot carry it).
- **A public relay hub** — an extra host to run; not needed while sites can open one UDP port.
